## 一、能力实测结论（probe_capability.py）

**104 项可用 / 9 项不可用。** 9 项不可用的全部是 V8R3 旧函数名与 Oracle 专有函数，不影响设计。

### 1.1 数据类型 —— 全部可用（比预期乐观）

Oracle 模式下 `JSONB` / `JSON` / `SERIAL` / `BIGSERIAL` / `GENERATED BY DEFAULT AS IDENTITY` / `BOOLEAN` / `CHAR(1)` / `TEXT` / `VARCHAR(n)` / `TIMESTAMP` / `CREATE SEQUENCE` **全部建表成功**。

> **影响**：计划中 Phase 6.1「DDL 类型降级」的紧迫性下降——不需要一个大的方言 DDL 层。

### 1.2 存储过程 —— plpgsql 与 plsql 都可用

`LANGUAGE plpgsql`（含 `$$` 包裹）、`LANGUAGE plsql`、Oracle 风格 `RETURN INTEGER IS ... END;`、函数内 `::jsonb` 强转**全部成功**。唯「不指定 LANGUAGE」报 `no language specified`。

### 1.3 标识符大小写

- `enable_ci = off` → **区分大小写**
- `enable_upper_colname = off`
- 未加引号标识符折叠为**小写**（实测建 `ProbeCaseUnquoted` → 存为 `probecaseunquoted`），**与 Oracle 折叠为大写相反**
- 加引号 `"ProbeCaseQuoted"` 保持原样

### 1.4 SQL 能力

`LIMIT` / `OFFSET` / `FETCH FIRST` / `EXCEPT` / `MINUS` / `INTERSECT` / `generate_series` / `WITH RECURSIVE` / `CONNECT BY LEVEL` / `DUAL` / 行值比较 `(a,b)>(1,2)` —— **全部可用**。

字符串聚合 `string_agg` / `listagg` / `wm_concat` / `group_concat` **全部可用**。`string_agg` 拼接 3000 行得到 30000 字符，**无静默截断**；无 `group_concat_max_len` 参数（即 Kingbase 不存在 MySQL 那个静默截断风险）。

### 1.5 系统目录与权限

`pg_tables`、`information_schema.*`、`pg_stat_user_tables`、`pg_stat_replication`、`pg_index`、`pg_constraint` 可用。`information_schema.columns.data_type` 取值是 **PG 风格**（`jsonb` / `varchar` / `bpchar` / `timestamp without time zone` / `integer` / `bigint`），**不是** Oracle 的 `NUMBER` / `VARCHAR2`。

`current_user = system`，`is_superuser = on`。

## 二、值归一化的实测陷阱（决定 `utils/normalize.py`）

| 表达式 | Python 类型 | `str()` |
|---|---|---|
| `1.0::numeric` | `Decimal` | `'1.0'` |
| `1::numeric(10,2)` | `Decimal` | `'1.00'` ← **同一逻辑值，text 不同** |
| `1::integer` | `int` | `'1'` |
| `0.1::float8` | `float` | `'0.1'` |
| `true` | `bool` | `'True'` |
| `'abc'::char(10)` | `str` | `'abc       '` ← **补 7 个空格** |
| `'abc  '::varchar(10)` | `str` | `'abc  '` ← 保留尾空格 |
| `'2024-01-01'::date` | **`datetime`** | `'2024-01-01 00:00:00'` ← **DATE 映射为 timestamp** |
| `'...+05'::timestamptz` | `datetime`(tz) | 渲染为 **+08:00**（会话时区） |
| `'abc'::bytea` | `memoryview` | — |
| `NULL::text` | `None` | — |
| **`''::text`** | **`None`** | — ← **Oracle 语义：空串即 NULL** |

```sql
SELECT (NULL::text IS NULL), (''::text IS NULL), (NULL::text = ''::text);
-- → [True, True, None]
```

**两个必须正视的结论：**

1. **Oracle 模式下 `''` 与 `NULL` 无法区分**——`SELECT ''::text` 在 Python 侧拿到的是 `None`。任何依赖区分二者的比较逻辑在此模式下不成立。
2. **`numeric` 的 scale 会污染 text 表示**——`1.0` 与 `1.00` 是同一逻辑值但 `::text` 不同。这正是"跨模式/跨列宽 SQL 侧哈希不可比"的直接证据。

## 三、缺陷复现证据

### 3.1 复现方法

在 node2 上 `SELECT pg_wal_replay_pause()` 暂停 WAL 回放，然后在 node1（主库）插入一行 `accounts.id = 0`。结果：

| 节点 | `accounts` count/min/max |
|---|---|
| node1（主） | (2001, 0, 2000) |
| node2（备，回放暂停） | (2000, 1, 2000) |
| node3（备，正常） | (2001, 0, 2000) |

**唯一真实差异：node1 与 node2 之间相差 1 行（id=0），且该行按主键排序位于最前面。**

`comparison.chunk_size = 1000`，node1 有 2001 行。

### 3.2 Bug #1 —— native 引擎假通过（`backends/native.py`）

```
Backend: native      Rows(A)=2001  Rows(B)=2000  →  Status: OK      Result: PASS
Backend: checksum    Rows(A)=2001  Rows(B)=2000  →  Status: DIFF    Result: FAIL
```

**同一对节点、同一时刻、同一张表**：checksum 正确报出差异，native 报 **PASS**。

根因：`_build_diff_query()` 两个分支生成完全相同的 SQL，`compare_table_native` 又把它交给单个连接执行，实际跑的是
`SELECT ... FROM public.accounts EXCEPT SELECT ... FROM public.accounts LIMIT 4` —— 恒为空集。

### 3.3 Bug #2 —— checksum 块错位（`backends/checksum.py`）

```
| public.accounts | 2001 | 2000 | 3/3 | DIFF |

- Chunk 0 (offset 0, limit 1000)    differs: ... vs ...
- Chunk 1 (offset 1000, limit 1000) differs: ... vs ...
- Chunk 2 (offset 2000, limit 1000) differs: checksum_a=2534...  checksum_b=ERROR
```

**1 行真实差异 → 报告 3/3 chunk（100%）全部差异。**

- 真实差异只在 chunk 0（id=0 落在第一块），chunk 1 完全无辜却报差异——OFFSET 使块边界整体位移
- 还多出**幻影 chunk 2**：`total_chunks` 由 `max(rows_a, rows_b)=2001` 算出 3 块，但 node2 只有 2000 行，`OFFSET 2000` 取空 → `checksum_b = NULL` → 显示为 ERROR
- 结论：工具既**夸大了差异范围**，又**完全无法定位**真实差异

### 3.4 缺陷 #8 —— 表名大小写不匹配时静默返回空

```sql
-- 建表 probe_case_tbl，用小写名查：
SELECT column_name, data_type FROM information_schema.columns
 WHERE table_schema LIKE 'pg_temp%' AND table_name = 'probe_case_tbl';
-- → [['id','integer'], ['v','varchar']]

-- 用大写名查同一张表：
... AND table_name = 'PROBE_CASE_TBL';
-- → []        ← 静默为空，不报错
```

`get_primary_key()` / `get_column_info()` 用参数化相等比较，命中此陷阱时会静默返回空列表，进而让 checksum 引擎降级为"仅行数比对"、native 降级为"比较所有列"——**不报错，但结论无意义**。
